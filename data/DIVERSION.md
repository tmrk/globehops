# Diversion coverage

GlobeHops has an optional routing core inspired by EDTO/ETOPS: it illustrates access to **potential diversion airports** while avoiding applicable restricted airspace in the same search. It is **not an operator's authorisation**, dispatch advice or a suitability assessment. In the app, **Diversion-aware routing** in the display menu switches it (`globehops:diversionRouting`, on by default; links can set `diversion=0|1` for a visit). Agent and MCP results stay great circles unless a request includes `routing: { "diversion": true }` (or a number of minutes, 60–370).

Three concepts remain distinct: a potential diversion airport passes limited public runway-data filters; modelled coverage is a geometric distance calculation; an approved/nominated en-route alternate is an operational choice requiring aircraft, operator, aerodrome and day-of-flight assessments that GlobeHops cannot make. Generated records and results use the first two terms, never a claim of compliance.

## Rules and assumptions

- ICAO Annex 6 Part I Amendment 36 replaced the term ETOPS with EDTO, covering aeroplanes with two or more turbine engines beyond a threshold set by the State of the Operator. The State also approves the operator's maximum diversion time. Departure and destination aerodromes may serve as en-route alternates. See [ICAO Doc 10085, foreword and definitions](https://www.icao.int/sites/default/files/APAC/Meetings/2019/2019/2019%20EDTOBangkok/10085_cons_en.pdf) and [ICAO's EDTO course, basic concepts](https://www.icao.int/sites/default/files/sp-files/SAM/Documents/2014-EDTO/EDTO%20Module%20%202%20%E2%80%93%20Basic%20concepts.pdf). These are principles behind the illustration, not operational rules implemented by it.
- For twins, the FAA threshold is 60 minutes from an adequate airport at the approved **one-engine-inoperative (OEI) cruise speed, under standard conditions in still air**. The speed is aircraft/operator specific. See [14 CFR §121.7](https://www.law.cornell.edu/cfr/text/14/121.7), [§121.161](https://www.law.cornell.edu/cfr/text/14/121.161) and [AC 120-42B](https://www.faa.gov/documentlibrary/media/advisory_circular/120-42b.pdf).
- [Part 121 Appendix P, sections I(e)–(i)](https://www.law.cornell.edu/cfr/text/14/appendix-P_to_part_121) provides 180-minute authority, flight-by-flight 207-minute North Pacific extensions, and 240-minute exceptions for North Polar/north of NOPAC/Pacific north-of-equator operations. Regular 240-minute and beyond-240 approvals cover specified Pacific US West Coast–Australia/New Zealand/Polynesia routes, the South Atlantic, Indian Ocean and Australia–South America oceanic areas. Operators should make every effort to plan maximum diversion distances within 180 minutes; this does not mean flying arbitrarily long detours to do so.
- [EASA AMC 20-6, chapter III section 1](https://www.easa.europa.eu/en/document-library/easy-access-rules/online-publications/easy-access-rules-acceptable-means?page=8) describes 60 minutes at approved OEI speed (standard conditions, still air) for twins with at least 20 passenger seats or MTOM at least 45,360 kg, and 180 minutes for at most 19 seats **and** mass below that value. Distinguish that older AMC wording from [current CAT.OP.MPA.140](https://www.easa.europa.eu/en/document-library/easy-access-rules/online-publications/easy-access-rules-air-operations?erules-id=ERULES-1963177438-12783): performance class A with at least 20 seats uses 60 minutes; at most 19 seats uses 120 minutes, extendable to 180 for turbojets with authority approval. [EASA's clarification](https://www.easa.europa.eu/en/faq/19164) explains the latter approval. The supplied older [CAA link](https://regulatorylibrary.caa.co.uk/965-2012/Content/Regs/06690_CATOPMPA140_Maximum_distance_from_an_adequate_aerodrome_for_two-engined_ae.htm) now redirects to a missing-page/login screen. No passenger-count or mass-based legal rules are inferred in this model.
- The A350's illustrative 300-minute / 2,000 nm and 370-minute / 2,500 nm figures appear in [ICAO's course, slide 15](https://www.icao.int/sites/default/files/sp-files/SAM/Documents/2014-EDTO/EDTO%20Module%20%202%20%E2%80%93%20Basic%20concepts.pdf); [Rolls-Royce](https://www.rolls-royce.com/media/our-stories/discover/2019/trent-xwb-etops.aspx) confirms 370 minutes / 2,500 nm. These imply approximately 400–405 kt; 400 kt is a representative **assumption**, not a certified speed for every aircraft. [EASA's A350 announcement](https://www.easa.europa.eu/en/newsroom-and-events/news/easa-certifies-airbus-a350-xwb-370-minute-etops) separately confirms certification to 370 minutes. Contemporary Airbus announcements were also reproduced by [Airport Technology](https://www.airport-technology.com/?p=123238) and [World Airline News](https://worldairlinenews.com/2014/10/16/easa-certifies-the-airbus-a350-900-for-up-to-370-minutes-etops/).
- ICAO Annex 14's code-letter-E runway width is 45 m (787/777/A350/A330 class): see [ICAO's runway-width discussion](https://www.icao.int/Meetings/AMC/MA/2004/APANPIRG15/wp12.pdf). Width alone says nothing about pavement strength or aircraft compatibility.

The default data profile is `twin-180`, model version 1: **180 min at 400 kt TAS (ISA, still air)**. Callers can construct profiles for 60–370 minutes with another positive OEI speed. The 60-minute threshold is informational only, never a routing obstacle. No aircraft type, engine count or operator approval is inferred; in particular this twin illustration does not automatically constrain quads.

## Dataset and eligibility

[OurAirports airports.csv](https://davidmegginson.github.io/ourairports-data/airports.csv) and [runways.csv](https://davidmegginson.github.io/ourairports-data/runways.csv) are public domain, without accuracy guarantees ([dictionary](https://ourairports.com/help/data-dictionary.html)). The independent dataset contains 2,626 potential diversion airports, **90,517 bytes / 38,004 bytes gzip** at this build. It does not alter searchable `airports.json`, its hash or its licence; it also stays separate from the ODbL time-zone table.

Only large/medium airports with valid positions qualify. Reviewed misplaced-airport exclusions from `excluded-airports.json` also apply. A runway must have `closed != 1`, a recognised hard surface, length at least **2,000 m** (6,562 ft), and width at least **44 m**. The width tolerates imperial rounding of a nominal 45 m runway (147/148 ft). Values are tested in metres before output rounding. The longest qualifying runway wins; equal lengths use the lowest runway id. Airport codes prefer valid IATA, then ICAO, GPS and ident; numeric OurAirports id remains the identity. Coordinates round to 0.01°, dimensions to whole metres; no attributes are invented.

The conservative free-text mapping accepts ASP/ASPH/ASPHALT, CON/CONC/CONCRETE, BIT/BITUMEN, PEM/PAVED and asphalt/concrete mixtures, including recognised G/F/P/E quality suffixes. Surfaces containing turf, grass, gravel, dirt, earth, water, sand, coral, mats, snow or ice do not qualify. Blank, UNK, single letters and unrecognised descriptions stay unknown, including apparent misspellings. Every observed string and its mapped category/count is recorded in [diversion-build.json](diversion-build.json). Missing width and OurAirports' occasional `-1` unknown-dimension sentinel never qualify. Unknown length is excluded as length evidence missing. Lighting is recorded for the chosen runway, **not required**: for example Honolulu's source flags read zero.

This build used 86,345 airport and 48,412 runway rows. Airport exclusions: 81,063 by type, 1 reviewed misplaced record, 0 invalid positions, 2,655 remaining candidates without a qualifying runway. Among runways attached to eligible airport candidates, the mutually exclusive rejection order/counts are:

| Reason                                         | Runways |
| ---------------------------------------------- | ------: |
| Closed                                         |     426 |
| Unknown surface or width (`excludedUncertain`) |     314 |
| Unpaved                                        |     455 |
| Insufficient/unknown length                    |   2,592 |
| Insufficient width                             |     515 |
| Qualifying                                     |   3,256 |

`excludedUncertain` counts a runway once even when both surface and width are unknown. Airport and runway counts have different denominators and must not be added together. Chosen-runway lighting: 2,365 lighted, 261 unlighted, 0 unknown. The build record also lists each chosen `[airportId, runwayId, lighted]` tuple (`null` for unknown lighting). The initial cached snapshot has null upstream commit and HTTP Last-Modified values; file hashes establish reproducible inputs, not a precise upstream revision. Fresh downloads retain available provenance in the cache and build record.

## Geometry and routing

Distance uses `EARTH_RADIUS_KM = 6371.0088`, not a flat map. Radius is `minutes / 60 × knots × 1.852`: the default is **2,222.4 km**. A point's coverage distance is the minimum great-circle distance to eligible potential diversion airports **or the flight's own endpoints**, regardless of whether those endpoints pass the runway filter. With airspace avoidance enabled, airports inside any applicable **non-endpoint** zone are excluded, using the same day, operator, altitude and country exemptions as routing. With avoidance disabled all eligible airports count. There is no land/coastline preference or distance-to-land penalty.

1. Test the exact great circle against zones and coverage. A clear and covered arc remains `path: null`, diversion `covered`; this common case does not build a binary coverage grid.
2. Otherwise run **one combined A***: a cell is blocked by an applicable non-endpoint zone **or** missing conservative coverage. The existing 0.5° grid, 16 moves, antimeridian/polar wrapping, string pulling, tightening, corner rounding and ≤1° densification remain. An independent airspace-only route supplies the length baseline and fallback; it is never patched with a second coverage detour. If that baseline already meets exact coverage it is retained with `covered` and zero extra distance.
3. Cap rasterisation computes each row's longitude half-width from `acos((cos(radius/R) − sin(lat)sin(airportLat)) / (cos(lat)cos(airportLat)))`, splitting spans across the antimeridian and handling full polar rows. A centre qualifies only within **radius − 40 km**, more than half a cell's maximum diagonal. Cache at most four base grids by radius and excluded id set (plus dataset hash); add endpoint caps to a temporary copy. Exact nearest queries use a latitude-sorted index, stopping when latitude separation exceeds the current nearest spherical distance.
4. Validate the whole final polyline against both zone outlines and coverage. Coverage samples are **≤0.1°** apart; every sample must have at least **half its actual arc-sample spacing** of spare radius. Nearest-point distance is 1-Lipschitz, so every intervening point is within the radius as well. Rounded corners and the unrounded fallback receive the same checks; neither can escape coverage. Zones retain their existing ≤0.1° outline sampling, not a new claim of analytic segment/polygon intersection.
5. Accept a covered candidate only within the existing `2.2 × GC + 500 km` airspace limit **and** the coverage allowance **`max(150 km, 0.08 × baselineKm)`**. Baseline is GC when clear, otherwise the airspace-only detour. Then report `adjusted`, with the incremental distance. Otherwise show the baseline with `gap`, preserving its airspace status. A `gap` means no acceptable route was found under this conservative grid/allowance policy, not a proof that every continuous path is impossible.

The allowance remains at the proposed 8%: GRU–JNB adds 53 km (0.72%), JNB–PER 441 km (5.31%), and AKL–SCL 606 km (6.28%), all useful modest adjustments. SYD–SCL's candidate was 12,397.8 km, adding 1,057.4 km (9.32%) against a 907.2 km allowance; CPT–EZE's candidate added 794.0 km (11.53%) against 550.9 km. Both are deliberately rejected. Enlarging the allowance would turn them into lengthy covered examples where airlines can instead seek beyond-180 authority; FAA Appendix P explicitly identifies these remote oceanic regions. These thresholds are an illustration calibrated on these routes, not measured airline preferences.

`maxMin` is the ceiling of the largest sampled nearest-airport distance divided by assumed OEI km/min on the **final shown route**, using the same excluded-airport set. `outsideKm` is route distance outside the profile limit, zero except for `gap`; `extraKm` is incremental flying distance, zero except for `adjusted`. `beyondThresholdKm` is route distance outside the 60-minute threshold, informational for every status. Distance totals use ≤0.1° samples with linearly interpolated boundary crossings (a numerical approximation, up to 11.12 km between samples); `maxMin` is a sampled maximum, not an operational worst-case guarantee. Coverage acceptance uses the rigorous spacing margin separately. A thrown internal error returns the existing safe GC fallback (`unavoided` when airspace was requested; `clear` otherwise) and **omits `diversion`**, rather than inventing metrics. Missing diversion data also leaves `diversion` absent.

## Performance, API and extension

Measured 9 November 2026 on Apple M4, macOS arm64, Node **26.5.0**, sequential `node scripts/bench-routing.ts` (CI uses Node 24). Three full dataset grid builds: **17.16 / 17.69 / 16.58 ms**. Cold default-profile routes with avoidance: CPH–JFK **12.03 ms**, SFO–HND **16.26 ms**, JNB–PER **27.43 ms**, GRU–JNB **23.50 ms**, SYD–SCL **34.10 ms**, HEL–NRT **74.95 ms**, FRA–ICN **50.60 ms**. Each leg in the script uses a fresh router; figures include zone rasterisation, coverage grid/search when needed, baseline search and final metrics. These are measurements, not latency promises; allow roughly 3–4× on mobile, which has not been measured here. Generous CI performance tests allow 1,500 ms for a grid and 2,000 ms for a cold routed leg to avoid machine-load flakiness.

`src/lib/router.ts` exports `createRouter({ airspace?, diversion? })`, `Router` and routing types. `RouteOptions` accepts `epochMs`, `operator`, `avoidAirspace` and nullable `diversion`. Null/undefined diversion preserves the legacy airspace result field-for-field without a `diversion` key (also checked directly against 1,176 pre-change results across airport pairs, operators and dates); both features off yield the exact GC distance. `createAirspaceRouter(dataset)` remains an airspace-only adapter with its original `dataset` property. Route caches include endpoint positions/countries, UTC day, operator, avoidance choice, profile id/version/minutes/speed, diversion content hash and airspace review date. Dataset instances are immutable after construction.

`useRouting(airspaceEnabled, diversionEnabled)` lazily imports each `?url` asset and starts one shared promise per dataset per page, including a settled failure. It returns `{ router, airspaceReviewed, failed: { airspace, diversion } }`; router is null until all enabled data settle, then uses the data that loaded. App passes no router at all when both features are off, so journeys are exactly the great-circle ones. Failed promises are not retried until page reload; the summary then says the data couldn't load.

The A* `edgeCost` function currently returns spherical step length. Its combined-search heuristic is great-circle distance to the goal cell, an admissible lower bound for that cost. Legacy airspace-only heuristics remain unchanged for shape compatibility. Future wind costs can use travel time per edge, provided the heuristic switches to distance divided by a valid maximum ground speed (or zero) and route-cache keys include the wind/time model. Published NAT/PACOTS tracks could become additional candidate graph edges or a separate track graph, checked against the same zone/coverage predicates; time-dependent tracks need date validity and cache keys too. No wind, track or airway model is implemented here.

## Limits and updates

Runways cannot establish RFFS category, hours, weather, NOTAMs, approach aids, fuel, pavement strength or permission. Wake, Pituffik, Diego Garcia and Eareckson illustrate the military-access problem: geometric proximity must not be interpreted as availability. Surface descriptions can be wrong or incomplete; conservative rejection can also remove usable fields. Winds, fuel reserves, terrain, aircraft systems, runway condition, NAT/PACOTS tracks, airways, ATC and real diversion procedures are absent. A spherical still-air distance and an assumed speed do not establish a safe diversion. The 207/240-minute regional exceptions and operator-specific beyond-240 approvals are not modelled. Real airlines often take different routes, including shorter routes with longer diversion authority.

Run `npm run diversion:build` to reuse `.cache/ourairports/{airports,runways}.csv`; absent files download with the same retry/content-type checks as `data:update`. `-- --refresh` downloads both again; `-- --offline` requires both cached files. The builder validates schemas, identities, dimensions, flags, production row-count/output floors and the decoded output before atomic writes. It writes compact `src/data/generated/diversion-airports.json` and the detailed `data/diversion-build.json`; **never hand-edit either**. HTTP provenance is cached separately; stale commit attribution is cleared when downloading files independently.

`data:update` now validates/caches runways alongside the original CSVs without adding them to the airport-search content hash. Its workflow change flag includes diversion-only changes, so daily automation rebuilds this dataset alongside time zones even when only qualifying runway evidence changed. Commit both diversion outputs. The cache-conditional drift test reproduces the entire file and build report; caches are never committed. Run `npm test -- scripts/diversion.test.ts scripts/lib/diversion.test.ts src/data/diversion.test.ts src/lib/diversion.test.ts src/lib/router.test.ts src/hooks/useRouting.test.ts`, and `node scripts/bench-routing.ts` after model/data changes. Raise `DIVERSION_MODEL_VERSION` for intentional coverage-policy changes; the API integrator owns the application release/version.
