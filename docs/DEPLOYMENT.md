# Deployment

GlobeHops is a static site on **Cloudflare Pages** at **https://globehops.marki.im/**. It moved there from GitHub Pages (`https://tmrk.github.io/globehops/`), which now serves only a redirect (see [Old GitHub Pages address](#old-github-pages-address)).

## Cloudflare Pages

The Pages project `globehops` (account `ca3dd86962a2421377c69ea022ca6887`, default domain `globehops.pages.dev`) is connected to `tmrk/globehops` through Cloudflare's GitHub app:

| Setting               | Value                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------ |
| Production branch     | `main`: every push deploys to production, including `GITHUB_TOKEN` pushes from workflows   |
| Preview deployments   | every other branch and pull request (`<hash>.globehops.pages.dev`, PR comments enabled)    |
| Build command         | `npm test && npm run build` (dependencies come from `npm ci`/`package-lock.json`)          |
| Output directory      | `dist`                                                                                     |
| Environment variables | `NODE_VERSION=24`, `BASE_PATH=/` (production and preview)                                  |
| Build image           | v3                                                                                         |
| Custom domain         | `globehops.marki.im`: proxied CNAME to `globehops.pages.dev` in the `marki.im` zone, HTTPS |
| Web Analytics         | off (the only measurement is the consent-gated GA4 in `src/analytics.ts`)                  |

A failing unit test or build stops the deployment and leaves the previous one live. Cloudflare reports each deployment to GitHub as a **Cloudflare Pages** check run on the commit (and comments preview URLs on pull requests). Change settings in the dashboard (**Workers & Pages → globehops → Settings**) or the [Pages API](https://developers.cloudflare.com/api/resources/pages/); `wrangler pages project list` and `wrangler pages deployment list --project-name globehops` show the current state.

The Vite base defaults to `/`. `BASE_PATH` can still build for a sub-path on another host (for example `BASE_PATH=/globehops/`). `vite.config.ts` falls back to `CF_PAGES_COMMIT_SHA` for the build commit when git is unavailable.

Host files live in `public/` and are copied to `dist/`:

- `_headers` caches content-hashed `/assets/*` for a year (`immutable`). Everything else keeps the Pages default (`max-age=0, must-revalidate` with ETags), so pages, `sw.js`, the manifest and agent files update as soon as a deployment finishes.
- `_redirects` sends any `/globehops/…` path on the new domain to the same path at the root (301), for links that only had their host swapped.
- `404.html` is generated by `scripts/localized-pages.ts` (one line per language, each linking to its app page). Without it, Pages would serve the app for every unknown path.

These three files are excluded from the offline precache (`scripts/pwa.ts`), because Pages never serves the first two and the 404 page is not part of the app.

## CI

`.github/workflows/ci.yml` runs on pushes to `main`, pull requests and manual dispatch: `npm ci`, lint, unit tests, a production build, then the three `@smoke`-tagged E2E tests on desktop Chromium against that build (`E2E_SKIP_BUILD: 1`): the first visit opens on the globe with its clock and suggestions, the globe renders, and every same-origin request stays under the base path. On failure it uploads the Playwright report for seven days. CI deploys nothing; Cloudflare builds the same commit in parallel. The full suite took about 12 minutes in CI and runs locally instead (`npm run test:e2e`, or affected specs only).

```sh
gh run list --repo tmrk/globehops --workflow ci.yml
wrangler pages deployment list --project-name globehops
```

To redeploy the current `main` without a commit, use **Retry deployment** in the dashboard or `curl -X POST -H "Authorization: Bearer <token>" "https://api.cloudflare.com/client/v4/accounts/<account>/pages/projects/globehops/deployments" -F branch=main`.

## Release tags

`.github/workflows/tag-release.yml` runs when a check run completes. It acts only on a successful **Cloudflare Pages** check run from the `cloudflare-workers-and-pages` app for `main`, that is, a successful production deployment. It reads the version from `package.json` at that commit and pushes the lightweight tag `v<version>` there unless the tag already exists, so the tag marks the first deployed commit of each release and is never moved. Check runs on commits pushed with `GITHUB_TOKEN` (data refreshes) start no workflows, which is fine because they never change the version. Manual dispatch tags the dispatched commit the same way. Versions up to 1.22.1 were tagged after GitHub Pages deployments (1.0.0–1.5.0 by hand on their last deployed commits).

## Airport and time-zone refresh

`.github/workflows/update-airports.yml` runs daily at **04:23 UTC** or manually. It downloads the three CSVs, validates and regenerates only when the content hash changes. When airport content changes, the workflow restores `.cache/timezones` using cache key `tz-2026f` and runs `npm run timezones:build` against the pinned TBB ZIP (downloading if absent), rebuilds potential diversion airports and the agent discovery files, then runs unit tests and a production build before committing the generated datasets and their build records to `main`. No-change airport checks skip the zone rebuild; this workflow does not upgrade the pinned TBB release automatically. Check source/licence changes explicitly when changing that pin.

The push uses the repository's `GITHUB_TOKEN`. Such pushes start no other GitHub workflows, but Cloudflare's GitHub app receives them like any other push and deploys the commit, so no explicit deploy step is needed. `agent/dataset.json` is always emitted from current metadata during the Vite build.

If branch protection rejects the push, the workflow pushes a dated `data/ourairports-YYYY-MM-DD` branch (which gets a Cloudflare preview) and attempts a pull request. Enable **Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests** for that fallback. Merging the PR to `main` deploys it.

```sh
gh workflow run update-airports.yml --repo tmrk/globehops --ref main
gh run list --repo tmrk/globehops --workflow update-airports.yml
```

## Old GitHub Pages address

GitHub Pages (**Settings → Pages → Source: GitHub Actions**) no longer hosts the app. `.github/workflows/pages-redirect.yml` publishes the small site in `.github/pages-redirect/` whenever those files change (or on manual dispatch):

- `index.html`, copied to `404.html` and to `en/`, `hu/` and `sv/` (with their own canonical address), replaces the location with `https://globehops.marki.im` plus the path below `/globehops/`, the query and the fragment. Every itinerary, compare, trip, locale and agent link therefore opens unchanged on the new domain. Without JavaScript, a meta refresh opens the new home page. GitHub Pages cannot send HTTP 301s for a project site; the canonical links and immediate client-side redirect are the permanent-redirect signal.
- `sw.js` replaces the app's offline worker for browsers and installed apps that still have the old version. It installs on their next update check, activates at once, deletes only GlobeHops's own `globehops-` caches (other projects share the `tmrk.github.io` origin), sends open windows to the same page on the new domain and unregisters itself. Saved preferences and remembered journeys belong to each origin, so they do not move; installed home-screen apps keep opening the old address until reinstalled from the new one, and are redirected each time.
- `llms.txt` tells agents that fetch the old guide where the current one is.

```sh
gh workflow run pages-redirect.yml --repo tmrk/globehops --ref main
curl -s https://tmrk.github.io/globehops/llms.txt
```

## Verify a release

Check that Cloudflare's **Cloudflare Pages** check run on the commit succeeded (or `wrangler pages deployment list --project-name globehops`) and that CI passed. Open `https://globehops.marki.im/?route=CPH-LHR-JFK` in a fresh browser context: confirm stops, totals, textured globe and labels. Reload, open About and test an airport search at desktop and mobile widths. Network requests for JS/CSS, fonts, `airports-*.json` and `earth-*.webp` must be same-origin and succeed. Confirm the About data date matches the committed build record for a data release. Do not infer live deployment success from a local build alone.

Also verify:

- About (and, on desktop, the bottom-left corner) shows the expected version (e.g. `v1.23.0`), and `/agent/dataset.json` reports the same `app.version` with the deployed commit.
- `/llms.txt` responds with 200 and readable discovery text. `/agent/capabilities.json`, `itinerary.schema.json`, `examples.json` and build-emitted `dataset.json` each respond with 200 and a JSON content type; check the freshness metadata against the committed records.
- A scheduled link such as `/?route=CPH-LHR-JFK&dep1=2026-11-20T08:15&arr2=2026-11-20T09:05&dep2=2026-11-20T11:00&arr3=2026-11-20T13:50` loads local endpoint times and journey totals.
- Day/night shading changes when scrubbing UTC time, the toggle restores the unshaded appearance, and playback moves through flights and transfers. Check reduced-motion behaviour and keyboard controls at desktop/mobile sizes.
- Direct reloads of `/en/`, `/hu/` and `/sv/` work, with translated HTML metadata and selectors. Ordinary Share links use the neutral root; Hungarian/Swedish UI loads city exonyms and localized place names.
- Follow aircraft tracks the plane, manual camera input exits it, and reduced motion re-centres only as needed. A combined `follow=1&leg=2` link preserves the aircraft camera without overwriting saved preferences.
- The hashed time-zone JSON loads, and visible credits retain TBB/OSM attribution and the ODbL link.
- An unknown path returns the 404 page with status 404, `/globehops/?route=CPH-JFK` redirects to `/?route=CPH-JFK`, and `https://tmrk.github.io/globehops/hu/?route=CPH-JFK#x` opens `https://globehops.marki.im/hu/?route=CPH-JFK#x`.

MCP is **not deployed**. `mcp/server.ts` is a local stdio process using a checkout and installed dependencies; Pages has no MCP endpoint. Its integration test is part of the unit suite.

The full browser suite can also run against the live site (no local server is started):

```sh
E2E_BASE_URL=https://globehops.marki.im/ npx playwright test
```

## Installed apps after a deploy

A successful production build emits `sw.js` containing every runtime asset's revision. Pages publishes the complete `dist/` atomically, so the worker never goes live ahead of its assets. Installed and browser apps keep serving their complete cached version until the next version installs successfully. Each opening explicitly checks the deployed worker, as do foreground resumes (throttled to 60 seconds) and reconnects. An Update/Later notice offers the waiting build; Update activates it and reloads controlled tabs once. Later keeps the current session and normal activation happens when all app windows close.

CDN propagation can still briefly expose mixed deployment bytes. New or changed precache downloads append `?__rev=<revision>` and use `cache: 'no-store'`; the worker verifies the exact response's SHA-256 prefix and retries once. A stale or missing file fails the entire install, preserving the previous offline version until a later update check retries. Unchanged files copy from the previous cache without downloading. Deployment changes are detected from `sw.js` bytes, not by querying GitHub commits. Cloudflare features that rewrite HTML (Email Address Obfuscation, Rocket Loader, Web Analytics injection) would break these hashes; the deployed bytes were verified to match every precache revision.

The first successful online visit must finish installing before offline use. Browser storage clearing or eviction can remove that copy; fullscreen/standalone apps request persistent storage where supported. Every runtime asset must be a same-origin build/public file so it is included automatically. Promotional splash, screenshot and social-preview imagery is deliberately excluded from the offline cache.
